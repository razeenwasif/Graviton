Architecture

How Graviton fits together

macOS has no Linux namespaces or cgroups, so a Linux container needs a Linux kernel. Graviton gives each container its own small VM, booted by Virtualization.framework in a fraction of a second, with a Rust agent as PID 1 that the engine talks to over vsock.

Isolation
One VM per container
Built

Like Apple's own container tool, each container gets its own VM instead of sharing one big Linux VM like Docker Desktop. Containers are isolated by the hypervisor, and a VM boots in about a third of a second, so the cost is small. A shared-VM mode could come later to save memory with many containers.

Guest
Kernel and initramfs
Built

scripts/build-kernel.sh compiles Graviton's purpose-built arm64 Linux 6.12.118-graviton kernel (8.2 MiB, zero loadable modules; vsock, virtiofs, ext4, overlayfs, balloon and binfmt_misc compiled in; 183–191 ms cold boot). scripts/build-guest.sh bundles it automatically with a 2.2 MiB initramfs carrying graviton-agent as /init and static busybox (keeping --alpine as an Alpine linux-virt fallback).

Channel
The agent over vsock
Built

The agent mounts /dev, /proc and /sys, loads the vsock and virtiofs modules, and listens on port 1024. Each connection gets ready, then takes requests:

→ {"op":"prepare","container":"a1e4…","layers":[…]} ← {"event":"prepared","files":514,"ms":42} → {"op":"exec","argv":["cat","/etc/os-release"],"container":"a1e4…",…} ← {"event":"started","pid":31} ← {"event":"stdout","pid":31,"data":[…]} ← {"event":"exited","pid":31,"code":0} → {"op":"shutdown"} powers the VM off
macOS
Signing and the VM queue
Built

Virtualization.framework only runs in a process signed with com.apple.security.virtualization; scripts/dev-gravitond.sh signs gravitond ad hoc for development. Every call on a VZVirtualMachine happens on its own dispatch queue, and completion handlers report back over channels, so the rest of the engine stays plain Rust.

Known gaps

Rough edges in what's built.

  • Container files live on the container's own disk
    Built

    Each container has a sparse disk image, formatted ext4 on its first start and kept until grav rm. A stopped container starts again with the files it changed, without unpacking its image again (94 ms instead of about a second for Alpine). The unpacked image is flushed to disk before the container runs, and a 16 MB journal keeps a powered-off disk consistent.

  • Build gaps
    Built

    grav build now supports Dockerfile heredocs (RUN <<EOF / <<-EOF with #! shebangs, inline shell heredocs, and COPY <<EOF / <<'EOF'), ADD <http(s)://url> with --checksum, --chmod on COPY/ADD, real persistent RUN --mount=type=cache (reclaimed by grav prune), ephemeral RUN --mount=type=secret (via --secret id=...,src=... or env=...), type=bind and type=tmpfs mounts, and hard links kept as tar LNKTYPE entries in layers. Still out of scope: ONBUILD and building from a Git URL.

  • Image export, import & commit (grav save / load / commit)
    Built

    grav save and grav load stream dual-compatible OCI + Docker manifest.json tarballs (gzip or uncompressed, single or multi-arch) over Unix sockets, cross-Mac TLS, and Docker Engine REST (GET /images/get, GET /images/{name}/get, POST /images/load). grav commit and POST /commit snapshot live or stopped containers with -a/-m/-c metadata updates while enforcing rootfs device-boundary isolation so mounted -v volumes are never swept into committed layers.

  • Real-time log streaming (--follow, --since, --until, --timestamps)
    Built

    gravitond broadcasts live LogEvent::{Line, Ended} notifications (zero polling) across Unix sockets, cross-Mac TLS, and Docker REST GET /containers/{id}/logs. grav logs and grav compose logs support -f/--follow, -t/--timestamps (RFC 3339 millisecond precision), --since, --until (RFC 3339, Unix seconds, or compound durations like 1h30m), and -n/--tail <N|all>, while non-detached grav run receives exit codes directly on LogEnd.

  • Copying files in and out (grav cp & Files tab)
    Built

    grav cp copies files and folders in both directions (plus - stdout tar), locally and over TLS, preserving modes, symlinks and hard links (mapping uploaded host UIDs to root:root). The Mac app's Files tab adds Upload…, Download… (toolbar, row menu and preview pane) and Finder drag-and-drop on both local and remote Macs. Stats still keeps five minutes in memory, so history starts over when gravitond restarts.

  • Per-container PID namespace, orphan reaping & HEALTHCHECK
    Built

    Every container now boots inside its own Linux PID/mount/UTS/IPC namespaces with /init acting as PID 1 (mounting container-local /proc, forwarding shutdown/interrupt signals cleanly to PID 2, and reaping orphaned/zombie processes via waitpid(-1)), while subsequent exec and -it sessions enter the same namespaces and top/stats report inner container PIDs. Full HEALTHCHECK probing runs end-to-end across Dockerfiles, Compose (healthcheck: + condition: service_healthy), grav run --health-*/--no-healthcheck, Docker REST v1.47, and Mac/iOS Inspect + Status pills. VM vCPUs/memory remain the resource limit.

  • Registry gaps
    Built

    grav login / grav logout / grav login --list support Bearer and Basic auth for private OCI registries (Docker Hub, GHCR, custom registries), storing passwords in the Mac's login Keychain and usernames in registries.json (0600). Pure-Rust ruzstd in graviton-agent unpacks single-frame, multi-frame and skippable-frame zstd layers, and grav pull plus the Mac and iPhone Pull sheets stream per-layer progress.

  • Image removal and cleanup
    Built

    grav df shows what images, container disks and the build cache take and what each would free; grav rmi removes an image no container uses; grav prune clears the build cache and layers nothing refers to, with --images, --containers, -a and --dry-run. Shared layers stay, and layers written in the last 10 minutes are kept. The Mac app has Clean Up… with a preview, and Remove… on each image.

  • Remote: the phone runs, pulls and controls
    Built

    From the phone you can run containers, pull images (with live per-layer progress), start, stop, restart, control Compose stacks, read logs, open shells, inspect Stats/Files/Inspect, follow the Activity feed, and receive APNs push alerts. Other Macs can do everything through grav --host and the Mac app. Pairing works on the local network (or over Tailscale by address), not through a relay.

  • Ports on every interface & UDP
    Built

    -p [IP:]HOST:CONTAINER[/tcp|udp] defaults to 127.0.0.1 and supports 0.0.0.0, [::], specific interface IPs, and per-client NAT UDP forwarding (with idle expiry and instant cleanup on stop). Host-to-guest TCP -p connections now tunnel directly over virtio-vsock (AgentRequest::DialTcp -> AgentEvent::Connected) with automatic fallback to guest NAT IP dials for older agents, bypassing macOS Local Network Privacy drops on headless LaunchAgents. Containers also reach each other at their addresses and by name (via guest DNS on 127.0.0.11:53), TCP and UDP, through a switch in gravitond beside the NAT.

  • Restart policies & daemon restarts
    Built

    Containers, settings and logs are saved; --restart no|on-failure|always (and the Restart picker in the Mac and iPhone Run sheets) restarts on exit with 1 s–60 s exponential backoff and automatically brings containers back when gravitond starts after a deploy or reboot. SIGTERM flushes running VMs cleanly without clearing want_running. Logs still keep growing on disk.

  • Mac app isn't sandboxed
    App Store only

    It reaches gravitond's socket in Application Support directly. Developer ID distribution doesn't need the sandbox; the App Store would, with the socket in an app group container or an XPC service.

Guest

The kernel and what boots with it.

  • A purpose-built kernel
    Built

    scripts/build-kernel.sh compiles Linux 6.12.118-graviton (scripts/kernel.config) inside a Graviton container with zero loadable modules and vsock, virtio, virtiofs, ext4, overlayfs, balloon and binfmt_misc built in: 8.2 MiB (down from 33.1 MiB Alpine), 2232 KiB initramfs, and 183–191 ms cold boot to agent-ready (~40% faster). scripts/build-guest.sh picks it up automatically when cached (--alpine keeps the Alpine fallback).

  • Rosetta for amd64 images
    Built

    VZLinuxRosettaDirectoryShare + binfmt_misc (OCF flags) run linux/amd64 binaries transparently inside chrooted containers. grav pull, grav run and grav build accept --platform linux/amd64 (also in the Mac Pull sheet), and amd64-only images automatically fall back to Rosetta when available.

  • Faster starts (VM snapshots & balloon)
    Built

    gravitond caches saved .vzsave VM states in a per-shape slot pool (up to 8 unique-identity slots/shape, ~13.5 MB/slot on APFS) with pinned per-slot MACs, dynamic -v mounts via VZMultipleDirectoryShare, BLKFLSBUF disk cache invalidation across container restarts, host UTC clock sync, and VZVirtioTraditionalMemoryBalloonDeviceConfiguration on every VM. SnapshotPool detects locked macOS console sessions via CGSessionCopyCurrentDictionary and -25308/-536870174 VmmError::SnapshotLocked fallback, preserving cached .vzsave slots without re-warm thrashing and exposing paused_reason in grav snapshot status. Managed via grav snapshot status|warm|clear, grav df and grav prune.

Apps

From the design canvas.

  • iPhone: Files and Stats
    Built

    Shipped in 10056f7: the iPhone app has native Swift Charts Stats (CPU, memory, network and processes), interactive Files browsing and file previews, Inspect (including Stack, Service, Rosetta architecture and Labels), plus Run and Pull sheets over TLS.

  • Docker Compose & Stacks
    Built

    grav compose up|down|ps|logs|stop|start|restart|build|config|ls runs multi-service stacks from compose.yaml / docker-compose.yml with automatic override merging, .env/${VAR} interpolation, YAML merge keys, build:, named & bind volumes, depends_on (including service_completed_successfully), and project-scoped service DNS aliases with zero cross-project collision. Both Mac and iOS group Compose containers into collapsible Stacks with one-click stack controls.

  • Fairy AI agent with Touch ID
    Built

    The Mac app's Ask Fairy panel (⌥⌘I) connects to Fairy.app over graviton.sock (full Fairy and Fairy Face, pinned to Antigravity gemini-4-neon-high) and exposes 27 engine/UI tools (Lyra a349898) over a private 0600 socket (fairy-tools.sock) with 64-hex-char per-turn tokens, covering both the local Mac and paired remote Macs — including pause/unpause, paused container filter, multi-arch platform builds (linux/arm64,linux/amd64), tag_image/push_image, and Compose log flags (timestamps/since/until). Voice replies default on (persisted), and conversations save to fairy-history.json (0600) with past-conversation search, resume, transcript copy, and deletion. Reads and safe reversible ops (start/restart/unpause, pull, tag_image, create volume, switch_host, navigate, dry-runs) auto-run; pause/stop/remove, run, exec, build, push_image, copy_files, remove_image, volume remove, prune, snapshots warm|clear, and compose up|down|stop|build require Touch ID via LocalAuthentication + inline Approval Card.

  • SwiftTerm is pinned to 1.11.2
    By choice

    It's the last release that draws with CoreText. Later ones render with Metal and need Xcode's Metal toolchain to build, a separate download. Moving up later means installing that toolchain first.

  • Volumes and Networks screens
    Built

    The Mac app's Volumes screen lists named volumes (disk size, file count, attached containers, inspector, create/remove, Finder reveal) alongside bind mounts, and the Networks screen shows the live L2 container switch, embedded DNS (127.0.0.11:53), connected containers with IPs & DNS names, and all published TCP/UDP ports. Both work locally, over TLS (my-server), and in demo mode, paired with grav volumes and grav network.

  • Pull progress per layer
    Built

    Request::Pull { progress: true } streams PullProgress updates over both the Unix socket and TLS (staying backwards-compatible with older clients that omit progress). grav pull renders live per-layer progress bars on TTYs, and the Mac and iPhone Pull sheets share GPullProgressView.

Running Graviton

Everything runs from the repo in ~/Github/Applications/Graviton; grav is cargo run -p grav --. This covers the working tree as of 10 Nov.

Getting started

  1. Build the guest

    scripts/build-guest.sh downloads Alpine's kernel and busybox once, cross-builds the agent with Rust's bundled linker (no extra toolchain), and writes the kernel and initramfs to Application Support.

  2. Boot a VM

    scripts/dev-gravitond.sh boot-check signs gravitond, boots a guest, runs uname -a in it and powers it off. Put your own command after --.

  3. Run a container

    Start the daemon with scripts/dev-gravitond.sh (or install it to start at login with scripts/install-launch-agent.sh), then grav run alpine cat /etc/os-release. Add -p 8080:80 for a port and -v ~/code:/app for a folder.

  4. Open the apps

    cd apps && xcodegen generate, then open Graviton.xcodeproj. The Mac app connects to gravitond when it's running; the sidebar card says which.

The Mac window

A sidebar for the sections, the containers in a table, and an inspector for the one you select. The window follows the design canvas: near-black surfaces, one periwinkle accent, and green, amber and red only for status.

Running a container

Run container in the toolbar, ⌘N, or Run… on an image card opens the sheet. It does what grav run -d does.

A container's logs

Double-click a container, or click Logs, to open it. Everything it prints is kept, with stdout and stderr together and Graviton's own messages first.

A container's terminal

Open terminal, or the Terminal tab, starts bash in the container (or sh if the image has no bash) at the size of the view, and follows the window as it resizes. The shell keeps running while you look at other tabs. When it exits, the tab shows the exit code and a New shell button. Copy grav command gives the same shell from Terminal: grav exec -it NAME sh.

On iPhone, the Shell tile on a container does the same over the TLS link, with a key bar for esc, ctrl, tab and the arrows above the keyboard. Terminals are drawn by SwiftTerm; colours are tuned for the near-black console, and programs can copy to the clipboard (OSC 52).

A container's stats

Stats samples a running container every two seconds and keeps five minutes. The figures come from the guest's /proc; each container has a VM to itself, so the VM's numbers are the container's. The colours passed the palette checks for colour blindness against the dark surface.

A container's files and settings

Files browses a running container read-only. The guest agent opens every path relative to the container's root (openat2 with RESOLVE_IN_ROOT), as a process inside would see it.

Inspect lists how the container was set up: the command it runs, working directory, user and hostname; the image's reference and digest; the VM's vCPUs, memory, kernel and folder; its address and published ports; volumes; and the environment, with values hidden until you show them. Copy as JSON gives the same as grav inspect, and Show VM Folder opens its console log and logs in Finder.

Images

Every image pulled with grav pull, grav run or the Pull sheet, from gravitond's local store. Without gravitond the grid shows sample images and Pull is disabled.

Building an image

grav build -t NAME ., or Build… on Images, builds from a Dockerfile without Docker. gravitond reads the Dockerfile, gives each step a cache key (the step as written, plus a hash of the files a COPY takes), and reuses the layer when the key matches. At the first step that misses, a builder VM boots with the folder shared read-only; RUN runs in a container there, COPY and ADD copy in, and after each step the agent writes what changed as a layer, deletions included. The image gets an OCI config and manifest and joins the local images, so grav run NAME works straight away. A rebuild with nothing changed takes no time and gives the same image.

Multi-stage builds work: each stage gets its own container in the same VM, COPY --from reads another stage's files (or an image's), and stages the target doesn't need are skipped. --target stops at a stage; --build-arg sets ARGs; --no-cache rebuilds every step.

Using another Mac

Any Apple-silicon Mac with Graviton.app can run the containers. On it, once: grav service install --remote (the engine inside the app, at login, open to paired Macs on port 7843), then grav pair for a code. Here: grav hosts add my-server.local CODE --name my-server, and check the fingerprint matches. From then on grav --host my-server … runs anything there, shells included, or grav hosts use my-server makes it the default. Builds send the folder over first, minus what .dockerignore leaves out; volume paths are paths on that Mac.

The pairing is pinned to the other Mac's certificate and its token is kept in hosts.json, readable only by you. The Mac app reads the same file: the Host menu (⌥⌘0 this Mac, ⌥⌘1… the others) or the name above the engine card switches which Mac the window shows, and Pair a Mac… pairs from the app.

Pairing a phone

On the Mac, run gravitond with --remote (or install the launch agent with --remote), then grav pair. It prints a one-time code, the Mac's address, its certificate fingerprint and a QR code. grav devices lists paired phones and grav devices revoke ID forgets one.
